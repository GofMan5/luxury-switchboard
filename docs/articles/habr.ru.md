# Один localhost для нескольких AI-провайдеров: desktop-switchboard на Go и Tauri

У AI-клиента обычно есть три настройки: адрес API, ключ и имя модели. Пока клиент один, а провайдер не меняется, этого достаточно. Но если клиентов несколько, появляется повторяющаяся работа: поменять endpoint здесь, заменить ключ там, вспомнить, какое имя модели принимает очередной upstream.

Luxury Switchboard переносит эти настройки в локальное desktop-приложение. Клиент обращается к одному адресу, а маршрутизация, ключи и порядок резервных провайдеров настраиваются за ним.

В статье — как устроен этот подход, почему обычного HTTP-проксирования недостаточно и где проходят его ограничения. Проект открыт под MIT; готовые установщики есть для Windows, Linux и macOS.

## Что находится между клиентом и провайдером

Схема первого сценария выглядит так:

```text
AI-клиент
    |
    | http://127.0.0.1:8798/v1
    v
локальный relay
    |
    +-- alias: my-chat -> provider A / upstream-model-A
    |
    +-- резервный маршрут -> provider B / upstream-model-B
```

Имя `my-chat` здесь задаёт пользователь. Оно не обозначает конкретную модель и не делает две модели эквивалентными. Это стабильное имя маршрута для клиента.

У маршрутов локального relay и публичного туннеля разные назначения. Для обычной работы туннель не нужен: он остаётся выключенным. Приложение также не является inference engine и не предоставляет бесплатные токены — пользователь подключает собственный доступ к провайдеру.

## Почему Go и тонкая оболочка Tauri

В проекте Go отвечает за relay, настройки, ключи, маршруты и историю. Tauri v2 запускает sidecar и связывает его жизненный цикл с desktop-окном; Rust-слой не дублирует правила маршрутизации. Интерфейс написан на React.

Команды между оболочкой и sidecar идут по версионированному framed stdio-протоколу: идентификатор запроса, типизированный payload, результат и отмена. Stdout предназначен для протокола, stderr — для диагностики. Это отделяет управление приложением от его сетевого API и не требует отдельного управляющего сервера для UI.

Код разделён на вертикальные сценарии: providers, keypool, routes, relay, analytics, guardrails, tunnel. Адаптеры HTTP, хранилища и stdio обращаются к application-слою, а не размещают правила предметной области в компонентах интерфейса.

Это не означает, что desktop-формат подходит всем. Если нужен центральный сервис с организационной авторизацией и эксплуатацией на сервере, такой набор требований стоит оценивать отдельно. Здесь отправная точка — локальный инструмент одного владельца.

## Почему не достаточно заменить Base URL

Слово «совместимый» скрывает несколько разных контрактов. Chat Completions, Responses и Anthropic Messages используют разные формы запросов и завершения ответов. Даже поддержка SSE ещё не гарантирует, что клиент получит ожидаемые события.

У relay есть несколько важных обязанностей:

- сохранять смысл завершения: ограничение длины и отказ не должны превращаться в успешный полный ответ;
- передавать tool calls, а не только текст;
- отличать завершённый поток от оборванного;
- прекращать работу при отмене клиентом, освобождая соединения и очередь;
- ограничивать буферы и размеры сообщений;
- не путать постоянный отказ с временной сетевой ошибкой.

В исходниках есть регрессионные тесты для таких случаев: перевода диалектов, streaming, отмены, retries и учёта usage. Это полезнее обещания «работает со всеми AI-клиентами». Конкретный клиент всё равно нужно проверять вместе с его моделью, инструментами и режимом streaming.

## Ключи, очереди и резервные маршруты

Пул ключей — не способ снять ограничения провайдера. Он позволяет явно управлять несколькими собственными credentials, их доступностью и очередью. Условия сервиса, квоты аккаунта и стоимость запросов никуда не исчезают.

Failover также нельзя свести к «получил любую ошибку — повторил у следующего». Сетевая ошибка, 429, постоянный отказ и незавершённый поток требуют разных решений. Повторный запрос может стоить денег; отказ по политике контента не должен провоцировать попытку обойти его сменой ключа.

В Model Routes можно сопоставить alias с upstream-моделью и задать порядок нескольких провайдеров. При этом резервная модель может отличаться по качеству, цене, контексту и поддержке инструментов. Стабильное имя маршрута не даёт стабильного поведения модели автоматически.

## Наблюдаемость без сохранения переписки в логах

Для диагностики полезно видеть, ожидает ли запрос очередь, повторяется ли после ошибки, сколько времени занял и сколько usage вернул провайдер. Для этого не обязательно сохранять полный prompt и ответ.

Live Activity показывает жизненный цикл запроса и безопасные операционные поля. Insights использует доступный usage и цены, заданные владельцем. Поэтому цифры расходов — оценка, а не замена счёта провайдера: пропущенный usage или неверный прайс не становятся достоверными только потому, что отображаются в таблице.

Есть короткие проверки доступности и полный профиль тестирования большого контекста. Такие проверки обращаются к upstream и могут расходовать платные токены. Скриншоты в репозитории используют вымышленные данные: отображённые задержки и суммы не являются измерением реальных провайдеров.

## Что здесь означает «локально»

У Luxury Switchboard нет собственного hosted control plane и аккаунта приложения. Конфигурация хранится локально и шифруется средствами ОС: DPAPI на Windows или desktop keyring на поддерживаемых системах. У encrypted persistence нет fallback на открытый текст. История находится в локальной SQLite.

Но «локально» не значит «offline» и не значит «никто не видит запросы»:

- провайдер получает предназначенные ему запросы и credentials;
- обнаружение каталога и тесты моделей обращаются к провайдеру;
- обновления загружаются с GitHub;
- подключение Codex использует соответствующие OpenAI sign-in/token endpoints;
- необязательный публичный туннель использует Cloudflare.

Другие процессы на том же компьютере также входят в модель доверия: loopback-адрес не является изоляцией от локального ПО.

У публичного туннеля отдельная граница: access key, разрешённые маршруты и явно опубликованные aliases. Его включение даёт обладателю ключа возможность создавать нагрузку на подключённые аккаунты. Это осознанное предоставление доступа, а не безвредный режим просмотра UI. Адрес quick tunnel меняется после перезапуска.

Guardrails тоже не стоит описывать как гарантию безопасности. Проверка выполняется локально, по умолчанию работает monitor-режим; правила могут пропустить проблему или дать ложное срабатывание.

## Минимальный первый запрос

1. Установить приложение из [актуального релиза](https://github.com/GofMan5/luxury-switchboard/releases/latest).
2. В Providers добавить совместимый endpoint и настроить аутентификацию. Для удалённого upstream нужен HTTPS.
3. Сохранить ключ в API Keys, если провайдер использует API-key authentication.
4. В Model Routes → Local relay → Add route выбрать провайдера и реально существующую upstream-модель. Задать публичное имя `my-chat`, оставить маршрут включённым.
5. Проверить адрес relay в приложении. По умолчанию это `http://127.0.0.1:8798`.

После этого для macOS/Linux можно отправить небольшой запрос:

```sh
curl --fail-with-body --max-time 120 \
  http://127.0.0.1:8798/v1/chat/completions \
  -H 'Content-Type: application/json' \
  -d '{"model":"my-chat","messages":[{"role":"user","content":"Reply with one short greeting."}],"max_tokens":32}'
```

Модель должна поддерживать этот сценарий или доступный перевод диалекта. Запрос использует ваш upstream и может тарифицироваться. Пример для PowerShell есть в [README](https://github.com/GofMan5/luxury-switchboard#make-your-first-request).

Если запрос не проходит, сначала стоит проверить состояние relay, включённый маршрут, точное upstream-имя модели и доступный ключ. В Live Activity можно увидеть статус, очередь и повторы. Этот пример не является заявлением о проверенной совместимости с конкретной IDE или агентом.

Windows-установщик сейчас не имеет Authenticode-подписи. На странице релиза опубликован SHA256SUMS.txt: сравнение хеша позволяет обнаружить несовпадение с опубликованным файлом, но не заменяет независимую проверку издателя.

## Где попробовать и что особенно полезно проверить

[Исходники Luxury Switchboard](https://github.com/GofMan5/luxury-switchboard) доступны под MIT. Там же находятся установщики и описание архитектурных ограничений.

Самая полезная обратная связь сейчас — не абстрактное «добавьте ещё моделей», а воспроизводимый сценарий: версия приложения, ОС, клиент, тип API, streaming/tools/images и минимальный запрос с вымышленными данными. Ключи, sign-in JSON, экспорт конфигурации и приватную переписку в issue прикладывать не нужно.

Какой клиент вам важнее подключить через один локальный endpoint — и какой его сценарий обычно ломает совместимые gateways?
